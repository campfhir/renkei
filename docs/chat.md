# The chat

Renkei's own conversational surface: `/[slug]/chat`. A person talks to the organization's model roster with their own tool access, keeps a history, groups chats into shared **projects**, attaches files, and inserts prompts from shareable **libraries**. Everything here lives in `apps/web` (`lib/chat/`, `app/[slug]/chat/`, `app/api/tenant/[tenantId]/chat/`) plus two small packages and two worker sweeps. See [`architecture.md`](./architecture.md) for where it sits in the topology.

## Access (`lib/chat/access.ts`)

One resolver family, the `agent_access_grants` rules generalized:

- Owner → `owner`. A named grantee → the grant's role while unexpired. A published project or library → `viewer` for anyone in the tenant.
- A chat is readable by its owner, a named viewer, or any member of the project it sits in (`resolveChatAccess`); only the owner may continue it. Nobody else resolves — null, surfaced as 404, never 403.
- Moving a chat between projects (`POST …/chats/[chatId]/move`) changes only `project_id`; the next turn picks up the new project's instructions, memory and toolset, and its members gain read access from then on.

## A turn (`lib/chat/start-turn.ts`, `turn-runner.ts`)

`POST …/chats/[chatId]/turns` does only what must precede the response: resolve the model (`resolveAgentLlm` — the request's model, else the chat's sticky one, else the org default), redact the typed text (below), and in one transaction insert the turn row, the prompt row and an empty `streaming` assistant row. It answers **202** with the ids and hands the rest to Next's `after()`.

`executeChatTurn` then resolves the tool surface, builds the prompt and history, and runs the loop:

1. `streamOrComplete(provider, …)` streams the reply. Every `LlmStreamEvent` is mirrored into the assistant row's blocks (flushed to the database on a timer that doubles as the heartbeat) and onto the turn's in-process channel (`turn-events.ts`).
2. If the reply ended in tool calls, they are run — the chat's local tools (`chat_read_attachment`, `chat_attach_to_sandbox`, `chat_write_file`, `project_memory_*`, and, outside a project, `chat_memory_*` and `chat_recall_chats`) in-process, everything else through the person's own MCP surface. Calls that only read (the catalog's `kind`, from the tool's `readOnlyHint`; a local tool's `readOnly`) run side by side, up to four at once (`toolGroups`), so a reply that searches three ways waits for the slowest search rather than the sum; anything that acts, or that neither source vouches for, runs alone and in the model's order, since its effect may be what the next call reads. Results are assembled in the model's order whatever order the calls finished in, and stored as a user-role `tool_results` row; a fresh assistant row is opened and the loop continues. Every file a tool returned in `_meta.renkeiDocuments` is kept as a `model`-origin attachment on that row (`storeArtifacts`; nothing is kept when the object store is unconfigured) and announced on the stream as an `artifact` event, whatever the turn's smaller budget let the model itself see. `chat_write_file` (`lib/chat/file-tools.ts`) is how the model makes a file of its own, by handing text back through that same door — one file per call, at most 1M characters, named by the model but never a path. The extension decides what is made: a text format (`.csv`, `.md`, `.json`, …) is kept as written; a document format is **rendered** from the text in `lib/chat/render/` — `.docx` (the `docx` package) and `.pdf` (pdfkit, standard fonts, so Latin text; anything else is reported back as a note) from Markdown through one shared block model (`markdown-blocks.ts`: headings, lists, tables, code, quotes), `.pptx` (pptxgenjs) from Markdown with a `#`/`##` heading per slide, `.xlsx` (exceljs) from CSV, JSON sheets or Markdown tables with numbers and dates typed. The model never produces bytes — the rule every byte path here keeps — and pays the same tokens for an `.xlsx` as for a `.csv`. The result sets `renkeiDocumentsShown: false` so the file is kept without being read back to the model. The tool is offered only when the org has a file store, and the system prompt then says so; without one the prompt says not to produce files at all.
3. Otherwise the turn completes. Limits: 10 minutes wall clock, 25 iterations, 60k chars per tool result, two rendered attachments per turn, and an hour in total spent waiting for permission (below), which is not counted against the wall clock.

### Permission

A call that changes something — anything neither the catalog (`kind: 'act'`, i.e. no `readOnlyHint`) nor a local tool's `readOnly` vouches for, so a Jira issue, a WebEx message, a memory note, a file the model writes, a git push alike — is not run until the chat's owner says so. Before such a call the runner (`askPermission`) writes the ask onto the turn row (`tool_permission`: the tool_use id, its name, the assistant row it sits in), emits `tool_permission_request` on the stream, and waits for the first of: the decision route's answer through the in-process channel (`TurnChannel.resolveToolPermission`), the same answer read off the row every two seconds (a replica that is not running the turn writes only the row), Stop, or the turn's permission budget (`permissionWaitMs`, an hour per turn, all asks together). The thread shows the ask inline where the reply stopped (`message-list.tsx`'s `PermissionCard`: what the assistant wants to do, what it will send, and **Allow once**, **Always allow**, **Deny**); a viewer of a shared chat sees the ask without the buttons. The same moment, a notification row of kind `chat_permission` is written for the owner and pushed (`lib/chat/permission-notification.ts`) — not gated on any preference, like an agent's approval card, because the turn is physically parked behind it; the push opens the chat itself, and answering the ask marks the row read.

`POST …/turns/[turnId]/permission` `{toolUseId, decision}` (owner only) records the answer: **always** first adds the tool's name to the person's `chatToolPermissions` preference (`lib/chat/permission-prefs.ts`: an `alwaysAllow` list and an `alwaysDeny` list, a name on both reading as blocked), so it is durable even if the turn dies before the call runs; then the answer goes onto the row and the channel. A decision for a call the turn is no longer waiting on is a 409. The runner honours **always** for the rest of the turn without another read, and every later turn reads the preference fresh at its start. **Deny** and a timeout feed the model an error result in place of the call's (`PERMISSION_DENIED_RESULT`, `PERMISSION_TIMEOUT_RESULT`) — the call is never made, the model is told to say what it was going to do rather than retry — and the turn goes on. The wall clock is paused for exactly the time waited; the turn's MCP token is minted to outlive the wait. A reload or a reconnect finds the ask on the turn (`TurnView.pendingPermission`, from the row), and a turn that ends mid-ask clears it. Nothing asks in org read-only mode, where no act tool is offered at all; `code_delegate` counts as one act — approving it approves what the sub-agent then does with the same tools. Nothing asks in a code chat's [auto mode](#code-projects) either, where the person has chosen to let the chat act; blocked tools stay blocked there too.

The Preferences page ("What a chat may do", `preferences/tool-permissions-form.tsx`) lists every act tool the person can reach (`lib/chat/permission-catalog.ts`: the catalog's act tools past every gate, grouped by connector, plus the chat's own act tools and a code project's), one collapsed fold per connector with a count of what is allowed or blocked on its line, and three answers per tool — **Ask** (the default), **Allow** (the same list Always allow writes to), **Block** — with an all-of-this-connector shortcut for each, saved as one document. A blocked tool is decided before it is ever called: the surface withholds it (`resolveChatToolSurface`'s `excluded`, and the local tools are filtered the same way), so the model is never offered the verb, and a call to the name from memory is refused without asking (`PERMISSION_BLOCKED_RESULT`).

Outside a project, `chat_memory_*` (`lib/chat/user-memory-tools.ts`, backed by `lib/chat/user-memory.ts`) mirrors `project_memory_*` scoped to `owner_subject` instead of a project — notes carried across every chat the person owns, rendered into the system prompt the same way project memory is. `chat_recall_chats` (`lib/chat/recall-tools.ts`) reaches into that person's _other_ chats: a keyword search over titles (plaintext) and a bounded, most-recently-active slice of decrypted content, or a plain listing when called with no query, and reading one chat back in full by id. Both are withheld entirely from a chat sitting in a project — a project's memory and history stay the project's own, and its chats are never "other chats" of the person's for recall's purposes.

Resend (`lib/chat/resend.ts`, `POST …/messages/[messageId]/resend`): the owner sends a prompt again, as it was or edited, and everything from that prompt on is removed first — the rows of its turn and every later one, those turns, and the files their replies produced (bytes best-effort after the rows). The prompt's own uploads survive the delete (it only unlinks them) and are linked to the new turn; then it is `startChatTurn` as usual. The page mirrors the cut with a client-only `truncate` event and follows the new turn as after Send.

Cancel: `POST …/cancel` marks `cancel_requested_at` and aborts the in-flight request when the turn runs in this process; other replicas see the flag on their next heartbeat. A runner that dies leaves rows the janitor (`createChatTurnJanitor`, every 5 min) marks `interrupted` once the heartbeat is 15 minutes stale.

### Tools (`lib/chat/tool-surface.ts`)

The chat calls the app's **own MCP endpoint** with a token minted for the turn (`@renkei/mcp-client`, application `agent`, `agent_id` null, the person's roles attached), exactly as the agents worker does — so capability projection, read-only mode, usage tracking and redaction all apply unchanged. What is offered is the intersection of the in-process catalog (`listAvailableTools`, authoritative for connector and app-only) and the endpoint's `tools/list` (authoritative for schemas), narrowed to the chat's toolset: `tool_config.connectors` on the chat, else the project's, else the default for the chat's kind — an ordinary chat's is the person's saved default (`tool-prefs.ts`), else the core set (`agents`, `cards`, `knowledge`, `sandbox`); a code project's chat starts from the person's saved **default for code projects** (a second preference key, `codeProjectTools`, kept apart from the chat default so one never leaks into the other), else the **code default** (`CODE_PROJECT_DEFAULT_CONNECTORS`: Bitbucket, GitHub, Jira, Confluence, `knowledge`, `sandbox` — the repository's host, the tracker and the wiki the work is described in, never the platform's agents and cards). In practice a code chat usually finds a toolset on its project: **a new code project is given its owner's code-project default (else the code default, Bitbucket and GitHub included) the moment it is created** (`POST …/code/projects`), so a later change to the preference leaves existing projects as they were made; the new-project form shows and can change it before creating, the project's page has the picker afterwards, and the picker's save actions in a code chat write the code-project default ("Save as my default for code projects"). Both personal defaults are edited on the Preferences page, each in its own section; `whoami` always; `*_preview` tools never (they render cards the chat cannot show). No token is minted when the toolset yields nothing. Only the core connectors are declared on every request — and, in a code project's chat, the pull-request and pipeline/workflow tools of Bitbucket and GitHub by name (`CODE_PROJECT_EAGER_TOOLS`), since the code brief tells the model to open the pull request outright; the rest of the toolset is reached through `find_tools` (`lib/chat/tool-discovery.ts`), whose matches join the request from the next model reply on. A discovery outlives its turn: every later turn reads the transcript for the tools earlier turns found or called and offers them again with their schemas, and a call to an enabled tool that was not offered surfaces it for the reply that follows — otherwise the model calls the tool it remembers with its types guessed, an array sent as JSON text.

### The request (`lib/chat/request-builder.ts`)

The system prompt carries a standing brief, the person, the project's instructions and rendered memory, and the files at hand. When `search_knowledge` is among the tools it also says when a search is worth making — the organization's own people, work and records, not general knowledge or what the conversation already holds — and to make one well-aimed search (`k` up to 10) and answer from it rather than re-searching with rephrasings; each search is an embedding call, a query and a live access check, so a reply that searches four times is slow and no better informed. History is the chat's rows repaired for the provider: thinking blocks are replayed only within the turn that produced them and only to the same Anthropic model (a switch mid-chat strips them — every turn resends the whole conversation anyway); a `tool_use` without its `tool_result` in the next row is dropped; empty blocks and failed rows are skipped; and the head is settled as a whole — leading assistant rows go, and a `tool_result` left at the head with no call before it (its call folded into the compaction summary, or in a leading assistant row just removed) is stripped, since every provider rejects one (the OpenAI dialect as a leading `tool` message, Anthropic as an unmatched result). Compaction keeps its boundary off a tool round for the same reason (`foldCandidates` folds the results row with its call), and a pass that runs inside a reply turn reports its own end on the stream (`compaction_progress` with `status`), so a reply that fails after a successful fold no longer reads as "Compaction failed.". Anthropic requests mark the system prompt and tool list for prompt caching and, when the chat has thinking on, ask for a budget of 60% of the org's output cap.

### Redaction (`lib/chat/outbound-redaction.ts`)

Tool results are redacted at the MCP boundary as always. What that gate never sees — the typed message, extracted attachment text, project instructions and memory — goes through the same detectors, policy and pseudonymizer on its way out, and the **redacted form is what is stored**, so the transcript equals what the model saw.

## Code projects

A **code project** is a chat project with a repository on it: `kind = 'code'`, reached from **Code** in the app menu's Chat section, beside Projects (`/[slug]/code`). The menu only opens the door — the Code page lists the projects and makes new ones, and a project's page lists the chats inside it, right under its environment; those chats also sit among the person's chats in the menu, marked with the Code glyph (`</>`) and naming their project beneath the title. It has a chat project's instructions, memory, toolset, sharing through `chat_project` grants and chats, but **no files of its own**: what a chat should have belongs in the repository, so files go into the checkout from a chat's Add files button, uncommitted, for the chat to use and commit. What it adds is that checkout and an environment, both held by the sandbox worker (`docs/sandbox-workspaces-design.md`) under the project's own scope (`lib/code/scope.ts`: the worker subject `code-project:<id>`, so one checkout, one uid and one environment per project, shared by every member). The project page is two columns on a wide screen: the repository's **file tree** on the left (`code/_components/repo-tree.tsx`, one folder fetched as it opens through `…/tree?path=` — from the checkout once a chat has made one, and from Bitbucket's source listing on the project's branch before that, so the tree is there without cloning anything), and the repository, environment, chats, README (folding), about and memory on the right; on a phone the tree folds above them. A project made without instructions starts from a standing developer's brief (`lib/code/default-instructions.ts`: read first, test-driven, small complete changes, the project's own checks, docs kept true, commits that explain themselves) — filled into the new-project form, and shown in the project page's instructions field until Save keeps it.

Creating one (`/[slug]/code/new`, `POST …/code/projects`) takes a name, a repository browsed on the person's own Bitbucket or GitHub — Bitbucket's workspace → project → repositories, or GitHub's account → repositories (no project layer), each searched by name across everything the person belongs to (`…/code/bitbucket/workspaces`, `…/code/bitbucket/projects`, `…/code/repos`, `lib/code/bitbucket-browse.ts`; `…/code/github/accounts`, `…/code/github/repos`, `lib/code/github-browse.ts`) — an optional branch, the text of a `.env`, and instructions. The repository is fixed from then on. The `.env` is parsed in the web app (`parseDotenv`, `@renkei/connector-sandbox`) and only its pairs reach the worker, which seals them and never returns a value; lines that were not variables are reported back once. **Nothing is cloned yet.** The first turn of a chat in the project clones the repository into the sandbox with the chatting person's own grant on the project's git host (`repo_provider`: Bitbucket or GitHub, `lib/sandbox/workspace-git.ts` dispatches the credential and clone URL by it) and runs the wait as the turn's **first step** — a `code_clone` step the runner writes into the transcript like a tool call (`PreludeStep`, `lib/chat/turn-runner.ts`), shown right after the prompt as "Cloning the repository…" and then "Cloned the repository" with its result, waited for up to five minutes, so the code tools are usable by the time the model speaks; a checkout the worker's sweep retired, or whose clone failed, is cloned again the same way on the next turn. The project page (`/[slug]/code/[projectId]`, `lib/code/project-view.ts`) shows the repository and the checkout's state (not cloned yet, cloning, ready with size and expiry, or failed with why), the repository's README from its host rendered as Markdown in place of a typed description (a section that folds, under the chats), and the environment, replaced by pasting a `.env` again or pruned one name at a time (`…/env`); it has no Tools button — the toolset is a chat's concern — and a back link to the Code page. Deleting the project (`DELETE …/code/projects/[projectId]`) takes the checkout and the variables with it.

A turn in a code project (`lib/code/turn.ts`) makes or waits for the checkout as above, runs under far higher limits than an ordinary chat (`CODE_TURN_LIMITS`: a thousand model calls, six hours, larger tool results — effectively unlimited until an organisation-level allowance exists), and adds the **`code_*` local tools** (`lib/code/tools.ts`) to the chat's own: `code_ls`, `code_find`, `code_grep`, `code_read_file`, `code_write_file`, `code_edit_file`, `code_run`, `code_git_status`, `code_git_commit`, `code_git_push`, `code_git_pull`, `code_env_names`, and `code_delegate`. They are bound to that one checkout — no argument names a workspace — and exist nowhere else: not in other chats, not on the MCP surface. The system prompt names the repository, the branch and the variable names, and carries a brief on working in it (read before editing, prefer exact edits, run the project's own checks, commit on a branch and push, never ask for or write a secret); when the checkout is not usable (cloning, failed, expired) it says so instead and the tools are withheld. A push or pull spends the chatting person's own grant on the project's git host for one worker call; a commit is authored as them. A write or edit answers with the file's diff against HEAD fenced in its result (the worker's `git-diff` verb, `sbWorkspaceGitDiff`), and a `code_run` with the working tree's changed files and counts; the chat renders a fenced diff as one (`code/_components/diff-view.tsx`, parsed by `lib/code/diff.ts`), one fold per file with +added −deleted, side by side on a wide screen and stacked on a narrow one. The code tools' calls carry their own names and git glyphs in the transcript (`lib/code/tool-labels.ts`; clone, commit, push, pull, branch, checkout, merge, rebase, stash, pull request in `components/icons.tsx`). **Sub-agents:** `code_delegate` (`lib/code/delegate.ts`) hands one self-contained task, with its own instructions, to a fresh model loop on the turn's model with the same tools minus pushing and delegating (the delegation itself is the act the owner is asked to allow — see [Permission](#permission); the sub-agent's own calls do not ask again); it runs up to `maxSteps` model calls (40 by default, 200 at most, 45 minutes), counts its usage against the turn, and answers with a report the orchestrating chat reads — which alone commits and pushes. A chat in a code project has a back link to its project and three more buttons in its title bar (`code/_components/code-chat-tools.tsx`): **Environment** opens the project's variables to look at, replace by pasting a `.env`, or prune; A code chat's title bar names, under the chat's name beside its project, the branch the checkout is on (`ChatView.projectBranch`, and `ChatListItem.projectBranch` under the same chats in the app menu) — read from `sandbox_workspaces.branch`, which the worker keeps current on every git verb, so the menu costs no worker call (`lib/code/branches.ts`); in the open chat it follows the checkout after every turn, from the same look that refreshes the Changes counts. **Add files** takes files picked or dropped straight into the checkout (`PUT …/code/projects/[projectId]/files?path=`, the body being the file; the worker's raw `/v1/workspaces/upload`) as untracked files the chat's tools then read, use and commit; and **Changes** — everything this chat did to the repository. Its button carries the checkout's uncommitted +added −deleted and the count of commits the chat made; the panel shows the uncommitted diff first (`…/code/projects/[projectId]/diff?context=`, 3 to 100 lines of context) and then, newest first, **the commits the chat made** — read off its own transcript (`lib/code/chat-commits.ts`: every successful `code_git_commit` result's "Committed on _branch_: _sha_ _subject_", and every later `code_git_push` of that branch), no table — each with where it stands now, asked of the worker per commit (`…/diff?commit=<hash>[&stat=1]`, the worker's `git-show` verb: _pushed_ when any remote branch holds it, _not pushed_ when only the checkout does, _not on branch_ when the checkout has switched since, _gone_ when it was cloned again), and its diff a click away at the same context setting. A button sends the chat the ask to commit, push and open a pull request.

**The code pane.** The repository is there to read and edit in the chat itself, not only through the chat's tools. A code chat's page splits its main column (`chat-thread.tsx` holds the layout, `code/_components/code-pane.tsx` the pane, `use-code-pane.ts` its state): the pane on the left, about 70% by default with a drag handle between and the ratio kept per browser, the chat on the right in its compact form — `compact` is now the chat column's measured width under 640 px (`lib/use-element-width.ts`), never the window's, so beside the pane the title bar folds as it does on a phone. A **Code** button in the title bar shows and hides it (remembered per browser, open at first). Under about 1024 px of main column — a phone always, a laptop with the app menu open sometimes — the same pane becomes the **Code** tab of a Chat | Code switch in the title bar, its badge the count of files with unsaved edits; the tab opens on the working tree's **Changed** files above the tree (`repo-tree.tsx`, which now opens files, marks changed ones M or A, and reads its open folders again when a turn ends), with Commit along the bottom, and a file opened over it with Save above the keyboard. Beside the chat the pane has a header (the tree's toggle, the open files as tabs with an amber dot when unsaved, Diff, Discard, Save, Commit with the count of changed files, a close), the rail, the editor, and a status line that says the one thing that matters — saved to the checkout but not committed, unsaved, or why it is read-only. The editor is Monaco on a screen with a pointer (`code-monaco.tsx`, loaded on demand; self-hosted and configured once in `lib/monaco/setup.ts`, which the admin script editor shares; the built-in tokenizers by extension, `lib/code/language.ts`, in two themes of its own that carry the chat's code palette, and no language service, since the client has no project-wide types) and a monospace text area with a row of accessory keys on a touch screen (`code-editor.tsx`) — coloured too, by the chat's highlighter drawing the same text beneath the transparent text area (`components/code-tokens.tsx`, `highlighterLanguageFor` naming its grammar). Files come from `GET …/code/projects/[projectId]/files?path=` — the checkout once there is one, the same bytes the tools see and the same env-value masking; before any chat has cloned, Bitbucket on the project's branch, read-only (`readSourceFile`) — each with an `etag` of the text as read. **Save is explicit** (the button, ⌘S), never automatic: the checkout is shared with the chat's turn and other members, and a half-typed line in the working tree while a turn runs its tests is a fine way to make a green build red. A save is the same `PUT …/files?path=` a person's upload uses, with `If-Match: <etag>` and `x-code-editor: save` (audit `code.files.saved`): a file that moved underneath is refused with 409 and the checkout's text, and the pane shows an amber banner with **Compare** (a unified diff made in the browser, `lib/code/text-diff.ts`, Myers over lines, drawn by the same `DiffView`), **Reload theirs** and **Keep mine** (a save without the header — an explicit overwrite, never the default). A turn ending reads every open file again: a clean one follows the checkout, a dirty one that moved gets the same banner. The chat's owner edits (the route also wants the editor role on the project); viewers, shared chats and the Bitbucket fallback read. **Commit** (`commit-dialog.tsx`) is the working tree's changed files with checkboxes — tagged _edited here_ when this browser saved them, _by the chat_ when the chat's tools wrote them in this thread, since git cannot say who changed a file in a shared working tree — a message, and the branch or a new one first, sent to `POST …/code/projects/[projectId]/commit`, which commits as the person the way `code_git_commit` does (audit `code.commit`); unsaved edits are named as not part of it, with a button to save them first. Then the dialog becomes the hash on its branch with **Push branch** (`POST …/push`, the person's own grant, `code.push`) and the ask that has the chat push and open the pull request. Both routes are editors-only and refused in org read-only mode (`lib/code/route-access.ts`). **The chat knows what was done.** A save, a commit and a push from the pane each become a **note row** in the transcript (`lib/code/notes.ts`, `note-text.ts`; `POST …/chat/chats/[chatId]/notes`, owner only, a structured note the server renders): user-role, kind `note`, stored and streamed like auto mode's nudge rows and shown as a small line, never the person's bubble (`PersonNote` in `message-list.tsx`; a saved file's name opens it in the pane). The next turn's model reads it in the conversation, so it knows a person changed those files by hand instead of finding a surprise in git status; `chat-commits.ts` counts a commit made here exactly like one the tool made, so the Changes panel and its badge see it; and the thread stays an honest log. A note is refused while a turn runs (the runner is the only writer then) and the page holds it — several saves of one file folded into one note — until the turn ends. A tool result's diff in the thread carries an **Open** link into the pane. Sketches and the decisions behind them: `docs/code-editor-design.md`.

**Sub-agents, and what the chat's context holds.** A code chat is an orchestrator, and its context is for coordinating: the brief (`CODE_BRIEF`) says to hand anything that takes more than a handful of tool calls — an investigation, finding every place a change touches, one self-contained piece of a change, a test suite run and fixed — to a sub-agent with `code_delegate`, one per piece, and to work from its report; what stays with the orchestrator is what is quick, a check of what a report claims, and the commit, the push and the pull request. A sub-agent's own file reads, searches, edits and test runs are its own conversation and never enter the chat's transcript — only its report does — but that conversation is **kept**: `chat_subagent_runs` (migration 112, `lib/chat/subagent-runs.ts`) holds one row per delegation, keyed by the `code_delegate` call's tool_use id, with the task and instructions, progress after every model call (steps, tool calls, the tool last reached for, tokens), the report, and at the end the whole transcript, sealed like a chat's messages. The runner hands each local tool call its own `toolUseId` and, in a code chat, a `SubagentRecorder` that writes the row and raises `subagent_progress` on the stream; the thread shows the delegation as a **sub-agent card** with the task, live counts while it works ("3 of 40 model calls · 9 tool calls · Reading a file"), the report's first line when it is back, and **View transcript** (`GET …/chats/[chatId]/subagents/[toolUseId]`, `subagent-modal.tsx`), which lists every model call with its prose and its tool calls the way the thread lists the chat's own work, polling while the run is still going. A turn that ends marks any run of its still running as interrupted; a resend removes the turn's runs with the turn. Nothing kept there is ever read back into a model's context.

On top of delegating, a code chat's history is trimmed: `buildHistory` with `elideEarlierToolResults` cuts every tool result of an **earlier** turn to its first 600 characters plus a note saying how much was cut and to call the tool again if it is needed (the current turn's results stay whole, and a `code_delegate` report is never cut — the report is the context worth keeping). The brief tells the model so.

**Milestones.** A reply's tool calls fold into one collapsed line (below), which is right for twelve file reads and wrong for the calls a person is waiting on. So a commit, a push, a pull, and every `bitbucket_*`/`github_*` call — acts by their verb (create, merge, approve, decline, trigger…), the rest reads, `lib/code/milestones.ts` — are lifted out of the fold as **milestone cards** in the reply, in order: a sentence of their own ("Committed", "Pushed to the remote", "Opened a pull request", "Read the pull request"), the tool's own first line as the headline (the commit's hash and subject, "Created pull request #12: …"), the tool's own link when it gave one, and the input and full result folded under. A commit's card has **View diff**, which opens the Changes panel on that commit. Nothing is guessed from the result: the headline is the tool's first line and the link is the tool's Markdown link, or nothing.

**Auto mode** (`lib/chat/auto-mode.ts`, `chats.auto_mode`, migration 111) is the composer's **Auto** switch in a code project's chat — the way Claude Code's auto mode works a task through without stopping at every prompt. On, two things change for the next Send. Nothing asks: every tool the chat may call runs without the permission card (`TurnPermissions.allowAll`); the person's blocked tools stay blocked, and org read-only mode still offers no act tool at all. And the turn does not end when the model stops talking: the model is offered `task_complete` (read-only, `{outcome: 'done' | 'needs_input', summary}`) and briefed to call it when the task is genuinely finished and verified, or when it truly cannot go on without the person; a reply that ends without a successful call to it is answered by the runner itself with a **nudge** — a user-role row of kind `nudge`, `AUTO_NUDGE_TEXT`, stored and streamed like a prompt but shown in the thread as a small note, never as the person's bubble — and the loop goes again inside the same turn (`AutoContinue` on the runner), so the one-running-turn rule, the code project's wall clock and Stop all still bound it. After `AUTO_MAX_CONTINUES` (20) nudges the turn completes as it stands. The `task_complete` call itself reads as a milestone card — "Task complete" with the model's summary, or "Needs your input" — and the switch is read off the chat row at the start of each turn, so flipping it mid-turn changes the next one. An ordinary chat stores the flag and ignores it.

## Streaming to the browser (`…/turns/[turnId]/stream`, `lib/chat/stream-events.ts`)

One `text/event-stream` per open turn, `runtime = 'nodejs'`. Besides the block-level events, the stream carries `tool_call_start`, `artifact`, `compaction_progress`, `subagent_progress` (a code chat's sub-agent, by its delegating call: steps, tool calls, the tool last reached for, and how it ended), and the permission pair `tool_permission_request` / `tool_permission_decided` (the ask a turn is parked behind, and its end; the reducer keeps it as `pendingPermission`, and a snapshot's `turn.pendingPermission` is authoritative). When the turn runs in this process the route subscribes to its channel and forwards events with sequence ids, replaying from the browser's `Last-Event-ID` after a reconnect (ring of 2,000). Otherwise — another replica, a restart, a ring gap — it sends the turn's rows as a `snapshot` and re-reads them every second, emitting only on change until the turn settles. The client reducer (`applyStreamEvent`) is shared with the server and treats a snapshot as "replace this turn's messages", so both paths converge on the same thread.

## Attachments (`lib/chat/attachments.ts`, `@renkei/blob-store`)

Uploads are raw bytes `PUT` to `…/chat/attachments?chatId=|projectId=`, capped by the org's `maxAttachmentBytes` before and after reading. Bytes go to the **organization's store** (`packages/blob-store`: an interface with an Azure Blob backend). An operator configures it on Organization → Storage (`connector_configs` row `blob-storage`, the account key sealed like any connector secret; `resolveTenantBlobStore(tenantId)`), with the deployment's environment (`BLOB_STORE_PROVIDER`…) as the fallback. The endpoint may be a Front Door domain that forwards to the account (`DEPLOYMENT.md`, "Storage behind Azure Front Door"): signing is by account and path, not host, and downloads and copies are unaffected because bytes always stream through the app. Neither configured means closed: uploads are off, the composer shows no paperclip, tools' files are not kept, and the system prompt tells the model not to produce files. An artifact opens a modal to download it or copy it to a connected network share (`…/attachments/[id]/copy`, through the upload executors, with the person's own credentials); text is extracted with `@renkei/document-text` (or decoded for text types), redacted and sealed. A prompt inlines an excerpt of each attached file's text (40k chars) and, for PDFs and images on Anthropic, a document/image block; the model pages through the rest with `chat_read_attachment` and stages bytes into the sandbox with `chat_attach_to_sandbox`. Downloads always stream through the app under a session check, as attachments with `nosniff`, never via signed URLs.

## UI (`app/[slug]/chat/`)

The chat has no chrome of its own: it fills the main column (`data-wide-page`), and the app menu (`app/[slug]/nav.tsx`) beside it carries the way in: **Chat** opens the most recent chat (`/chat` redirects to it, or to `/chat/new` with no history) and **+ New** starts one: `/chat/new` creates the empty chat there and then and redirects to its address, so the first Send is a turn like any other — the thread never changes address or reloads under the person. A chat nothing has been said in yet stays out of the menu, and one still empty a day later is swept. The chat list and its search sit under that section on every page — the tenant layout loads them (`loadChatSidebar`), archived chats included and flagged. That menu is now a column that stays open on a wide screen (the hamburger hides it and the choice is remembered in the browser) and a drawer below `lg`; it is grouped into sections, and its **Chat** section holds Chat, Projects, Prompt libraries and Memory plus the person's chats by day and the ones shared with them (`_components/chat-nav.tsx`, rendered on every page from the sidebar data the tenant layout loads); a "+ New" beside Chat starts a chat. Every row of the menu leads with a glyph (`components/icons.tsx`, hand-rolled: a house, a bot, a closed book with its ribbon, a folder; a round bubble, fanned pages, `</>`, a square bubble with lines, a brain), and so does every row of the account menu. **Code** sits in that section beside Projects; the code projects themselves are listed on its page, and the chats inside each are among the person's chats below, marked with the same `</>`. The chat draws its own frame flush under the top bar (`data-flush-page` drops the column's padding): a title bar with labelled Tools and Share buttons, the thread, and the composer on a tinted band along the bottom edge. The thread reads a reply across every assistant row of its turn as one sequence: text as Markdown (`react-markdown` + `remark-gfm` + `rehype-highlight`, raw HTML skipped, links open elsewhere without a referrer; a fenced block is a card with its language named in a header beside Copy, coloured by lowlight's common grammars plus the extras and fence aliases in `lib/chat/code-languages.ts` and `code-grammars.ts`, so `postgres`, `ts`, `yml` and `env` colour; a tool call's JSON input and result are coloured the same way by `_components/code-pane.tsx`), and every run of thinking and tool calls between texts as one collapsed line ("Thought · 3 tool calls", or what is happening right now while it streams) that opens to the steps in order, each call folded again with its result under it. The model menu in the composer picks the model and, for models that take one, switches extended thinking. The title bar names the chat (the owner renames it in place — the pencil, or a double-click) with the project it sits in as a subheading; the menu's rows lead with the mark of their kind — a round bubble for an ordinary chat, fanned pages for one in a chat project, `</>` for one in a code project — and show the title with the project's name beneath it when there is one (never the owner), and a funnel inside the search box picks which states the list shows — active, archived, or both; active only by default (Archive and Unarchive sit in the row menu beside Delete); its buttons drop to icons on a narrow screen so the name stays readable. Under each of the owner's prompts, **Edit** puts its text back in the box (Send then resends it in place of everything after) and **Resend** asks, then sends it again as it was. The title bar's **Artifacts** button lists the files tools produced in the chat, newest first, each a download through the app. The composer sends on Enter (touch keyboards use the button), uploads dropped or pasted files at once, switches model and thinking, narrows the toolset, and inserts prompts (`/` on an empty box). Viewers of a shared chat see a banner and no composer, but the stream still runs. While a turn waits for permission the collapsed line reads "Waiting for permission to call X" and the ask's card sits under the reply; Stop still cancels the turn.

## Voice (`lib/voice/`, `@renkei/voice`)

When the org has configured a speech service (the `voice` connector — one region or custom endpoint and one key, Azure AI Speech today, behind the vendor-agnostic `VoiceProvider` in `packages/voice`), the chat can be heard as well as read; when it has not, nothing about voice is rendered anywhere, so a person is never offered a control with no service behind it. `lib/voice/availability.ts` answers that question for the chat page and the preferences page in one call.

Three ways in, all beside the composer (`_components/voice-menu.tsx`, and a microphone next to it). **Dictation**: the microphone turns what the person says into text in the box — each utterance is transcribed and appended, to read over, fix and send like anything typed — for anyone who wants to talk without the full-screen mode. **Read aloud**: the person's preference (`user_preferences` key `voice`: voice, pace, language, whether the language spoken is detected, wave colour, and whether replies are read unasked; language and voice are searchable pickers in the menu and on Preferences alike — `_components/voice-picker.tsx` over `lib/voice/catalog.ts` — languages grouping their regions with the person's own first, voices grouped by language and region with the chosen language first, each with the vendor's word on it (Azure's `VoiceTag`, parsed into `VoiceInfo.description`) and a play button that says one sentence in the voice's language (`lib/voice/sample-phrase.ts`, a fixed sentence per language, Chinese in Chinese; `lib/voice/use-voice-preview.ts` plays it through a queue of its own after silencing a reply being read), and a search that finds a voice by name, language in English or in itself, country, or a word like "warm"; picking a voice of another language switches the language with it, a language change keeps a multilingual voice and drops one that cannot speak it) or a **Listen** button under any reply. The reply is spoken as it streams, not after: `lib/voice/use-reply-speech.ts` watches the turn's assistant text, `sentences.ts` cuts what has closed into sentences (never inside an open code fence), `speech-text.ts` turns each into words (headings and emphasis dropped, a code block becomes "Code omitted", a table is read row by row), and `speech-queue.ts` fetches each piece from `POST /api/tenant/[tenantId]/voice/speech` while the previous one plays. The pieces are played as one voice: each is decoded the moment it arrives and placed on the Web Audio clock right after the previous one (`gapless.ts`: the vendor's padding trimmed to the sound, a fixed sentence gap between pieces, a short fade at each cut), so the sound never stops between sentences and only a piece the vendor has not yet delivered leaves a gap. Alongside, one `<audio>` element loops silence for as long as a stream is open, or for the whole of a voice conversation (`SpeechQueue.hold`): it is the element that owns the device's media session, and with it looping a Bluetooth speaker or headset never hears the stream stop and reopen. Under a reply, Listen becomes Pause while it reads, with Stop beside it; Pause holds the clock (`pause`/`resume`, the state `paused`) and Resume carries on from the same sample. Stop — the composer's, the menu's, the Listen button's — is immediate and drops what is queued. **Voice conversation** (`_components/voice-mode.tsx`): a full-screen mode over the same thread that listens through the microphone (`lib/voice/recorder.ts`: an audio worklet at `public/voice-capture-worklet.js`, energy-based speech detection against an adapting noise floor, each utterance encoded as 16 kHz mono WAV and recognised whole by `POST …/voice/transcribe` — in whatever language it was said: the preference **Detect the language I speak** (`detectLanguage`, on by default) has the route ask the vendor which language it heard (`?detect=1`; Azure's fast transcription endpoint, which falls back to the short-audio one and the person's own language where it is not served), so nobody has to name their language before they are understood, and the Language preference only decides which voices are offered, how replies are spoken, and what is listened for with detection off. Dictation is recognised the same way. Detection is per utterance, so a turn in English and the next in Japanese need no change of setting, and the reply follows: the route answers with the language it heard, the thread keeps the last one heard (`heardLocale`, cleared when the Language preference changes) and reads replies in it, and the speech route stands in a voice that can speak it when the person's cannot — `voiceForLocale` in `lib/voice/catalog.ts`: their own if it speaks the language or is multilingual, else the org default, else a native voice of the language of the same gender, else a multilingual one; voice mode says "Heard in Japanese" under the utterance when that differs from the setting), sends each utterance as an ordinary turn — same chat, same project, same tools and model, so it works in a plain chat, a chat project and a code project alike — and reads the reply as it arrives. Speaking while the assistant is being read or written interrupts it: the voice stops and the turn is cancelled, and what was said is sent once the person pauses — a pause of about a second and a half, long enough that a breath or a search for the next word is not taken for the end of the sentence. For people whose thinking pauses were still being sent, or for a noisy room, the preference **Press to talk** (`pushToTalk`, off by default; Preferences only) makes the conversation a walkie-talkie: the recorder's `manual` mode starts nothing on its own — Talk interrupts a reply and opens the microphone and a take, Done closes and sends it and the microphone closes with it, Space does either, and ten seconds of silence or the transcription route's length cap closes it unasked. When the microphone is open is what decides how a Bluetooth headset sounds (any open microphone track holds it on its hands-free profile), so voice mode keeps it open only when it can be used: press-to-talk between Talk and Done; with echo cancellation off, only while the assistant is neither thinking nor speaking (the track is released when a turn starts and opened again when the reply is done; Stop makes that now); with echo cancellation on, throughout, because talking over a reply is how it is interrupted. While a reply is being worked out, voice mode says so rather than going quiet. A turn sent from voice mode carries `voice: true` (the turns route → `startChatTurn` → `buildSystemPrompt`), and the prompt's voice brief asks the model to say in one plain sentence what it is about to do before each tool call — "Looking for a slot with Priya and Marcus on Thursday" — which is read aloud as it streams like the rest of the reply, and to write prose that reads well aloud. A call the model did not introduce is announced by the page instead (`lib/voice/activity.ts`: "Searching Jira issues", the code tools' own sentences); the line under the wave shows the model's sentence or the page's; and twenty seconds of silence earns a "still working on it" — the page's lines spoken into the reply's own stream so they land in order with its text, and never after a Stop. A permission ask (the turn parked behind an act tool) is spoken the moment it is raised — "the assistant wants to create a Jira issue; say allow, always allow, or deny" — and shown as a panel with the same three buttons as the card in the thread; what the person says next is taken as the answer (`lib/voice/spoken-decision.ts`: always beats allow, no beats yes) and read back ("Allowed."), and speaking while an ask is open does not interrupt the turn, which is waiting rather than working. Leaving voice mode leaves the chat as the conversation went. What the person sees there is a wave (`_components/voice-wave.tsx`, canvas): its amplitude and the blurred glow behind it follow the microphone's level while listening and the speaker's while the assistant talks (`SpeechQueue.subscribeLevel`, an analyser tapped into the playback element), and with no sound to follow it idles slowly rather than freezing; its colour is the person's preference (chosen on Preferences alone; the speaker menu in a chat leaves the colours be), one for the assistant (a reply being read; a rainbow by default) and one for themselves (listening, dictating; emerald by default) so the two sides are never confused, and the same colours drive the small dancing bars in the composer while a reply is read or the microphone listens.

Echo cancellation is asked of the browser so the assistant's own voice, heard through the microphone, does not count as an interruption; it is a per-device choice in the speaker menu (`lib/voice/device-settings.ts`, localStorage, like the desktop-notification opt-in) because on some platforms asking for it moves playback onto a voice-call path — macOS voice processing, a Bluetooth headset's hands-free profile — where the assistant comes out one-sided or muffled the moment the microphone opens. With it off, the browser's noise suppression and automatic gain are off too — each alone is what makes an operating system treat the stream as a call and move a Bluetooth headset to its hands-free profile — the microphone is closed to speech while the assistant talks, and Stop is how a reply is cut short. On iOS the page's audio session (`lib/voice/audio-session.ts`, `navigator.audioSession`) is `playback` except while a microphone is actually open, so a headset returns to its stereo profile the moment recording stops — and that API, along with the built-in microphone's own recording route, only behaves this way once iOS has actually put the page in its standalone runtime, which is what `app/manifest.ts` and the `appleWebApp` metadata in `app/layout.tsx` ask "Add to Home Screen" for; without them the icon opens an ordinary Safari tab instead. The same menu chooses this device's microphone and, where the browser can route output (`AudioContext.setSinkId`; not Safari), its speaker — `enumerateDevices` ids kept in localStorage beside the echo choice; a chosen device that is not connected is the default until it is back.

The vendor's voice list is cached an hour per org (`lib/voice/config.ts`); the speech and transcription routes are rate-limited per person and per org (`lib/inbound-rate-limit.ts`) because every call is billed, and each successful call is written to the voice ledger (`voice_usage`, migration 110; `lib/voice/usage.ts`) as characters spoken and milliseconds of audio delivered, or milliseconds heard — never the text — for the Voice card on My usage and the listener and speaker boards on Organization usage (see [`agents.md`](./agents.md), "Usage ledgers"). Every voice route is session-guarded; the admin route (`/api/admin/[slug]/connectors/voice`, with a `/test` that lists voices to prove the key) is operator-only and records a `connector.configured` audit event.
